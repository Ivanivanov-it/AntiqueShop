SEO and performance improvement ideas
=====================================

This file expands the four recommended priorities from the project review.


1. Set the production site URL and add sitemap support
-----------------------------------------------------

Problem:
- astro.config.mjs does not define `site`.
- Astro falls back to the current origin during build/dev, so generated canonical,
  hreflang, Open Graph, Twitter, and JSON-LD URLs can become localhost URLs.
- public/robots.txt allows crawling but does not reference a sitemap.
- No sitemap.xml is generated in dist.

Suggested implementation:
- Add the real production domain to astro.config.mjs:

  export default defineConfig({
    site: "https://your-real-domain.com",
    i18n: { ... },
    vite: { ... },
  });

- Install Astro sitemap integration:

  npm install @astrojs/sitemap

- Add it to astro.config.mjs:

  import sitemap from "@astrojs/sitemap";

  export default defineConfig({
    site: "https://your-real-domain.com",
    integrations: [sitemap()],
    ...
  });

- Update public/robots.txt:

  User-agent: *
  Allow: /
  Disallow: /admin/
  Sitemap: https://your-real-domain.com/sitemap-index.xml

Notes:
- The exact sitemap filename should be checked after build. Astro often emits
  sitemap-index.xml.
- This is the highest priority because canonical and hreflang URLs affect how
  Google understands the Bulgarian and English versions of the site.


2. Optimize the homepage hero and stop loading Netlify Identity globally
------------------------------------------------------------------------

Homepage hero problem:
- src/pages/[locale]/index.astro uses `/images/hero-image.png`.
- The current hero image is around 2.4 MB.
- It is the first large visual element on the homepage, so it likely dominates
  Largest Contentful Paint.
- It has no responsive variants, so small screens still receive a large PNG.

Suggested hero implementation:
- Convert the hero to WebP or AVIF with multiple widths, for example:
  - hero-image-640.webp
  - hero-image-1024.webp
  - hero-image-1600.webp
  - hero-image-2200.webp

- Use srcset and sizes on the hero image:

  <img
    src="/images/hero-image-1600.webp"
    srcset="/images/hero-image-640.webp 640w,
            /images/hero-image-1024.webp 1024w,
            /images/hero-image-1600.webp 1600w,
            /images/hero-image-2200.webp 2200w"
    sizes="100vw"
    alt="..."
    fetchpriority="high"
    decoding="async"
    class="w-full h-full object-cover"
  />

- Consider adding width and height attributes if the rendered aspect ratio is
  stable enough.

Netlify Identity problem:
- src/layouts/Layout.astro imports `netlify-identity-widget` in a script that is
  present on every public page.
- The built public JS bundle is about 178 KB.
- Public visitors do not need the admin login widget on every page.

Suggested Netlify Identity implementation:
- Remove the global import from Layout.astro.
- Load Netlify Identity only on `/admin/`, or conditionally load it when needed.
- If public login redirects are still needed, use a small dynamic import only
  when the URL hash indicates a Netlify Identity action.

Example direction:

  if (window.location.hash.includes("invite_token") ||
      window.location.hash.includes("confirmation_token") ||
      window.location.hash.includes("recovery_token")) {
    import("netlify-identity-widget").then(({ default: netlifyIdentity }) => {
      netlifyIdentity.init();
    });
  }

Notes:
- This should reduce public JavaScript significantly.
- After changing this, test the CMS login/invite flow carefully.


3. Add product-specific schema and product social images
-------------------------------------------------------

Problem:
- Layout.astro emits generic Store JSON-LD on every page.
- Product detail pages do not emit Product/Offer schema.
- Open Graph and Twitter images always use the shop logo, not the product image.

Suggested implementation:
- Extend Layout.astro to accept optional SEO props, for example:
  - ogImage
  - ogType
  - structuredData
  - canonicalPath if needed

- Keep the global Store schema site-wide, but allow individual pages to add
  extra JSON-LD scripts.

- In src/pages/[locale]/antiques/[id].astro, generate Product schema:

  {
    "@context": "https://schema.org",
    "@type": "Product",
    "name": itemTitle,
    "description": itemDescription,
    "image": absoluteProductImageUrls,
    "category": categoryName,
    "offers": {
      "@type": "Offer",
      "price": data.price,
      "priceCurrency": "EUR",
      "availability": data.available === false
        ? "https://schema.org/SoldOut"
        : "https://schema.org/InStock",
      "url": canonicalUrl
    }
  }

- Also add BreadcrumbList schema on product pages:
  Home > Categories > Category > Product.

- Set product pages to use the first product image as og:image/twitter:image.
  Prefer the optimized 1200px version when available.

Notes:
- This can improve rich-result eligibility and link previews.
- It also gives search engines clearer product, price, and availability signals.
- Make sure absolute URLs use the configured production `site`, not localhost.


4. Harden image optimization filename handling and regeneration
--------------------------------------------------------------

Problem:
- scripts/optimize-images.js creates output names by lowercasing and stripping
  anything outside `[a-z0-9-_]`.
- Cyrillic names can become empty base names. Existing files like `-400.webp`,
  `-800.webp`, and `-1200.webp` show this has already happened.
- Different Cyrillic files can collide into the same optimized filenames.
- The script skips existing optimized files, so replacing an upload with a new
  image using the same filename will not regenerate variants.

Suggested implementation:
- Replace the current getBaseName() logic with safer transliteration or a hash.
- A hash is the safest and least ambiguous option.

Example direction:

  import crypto from "crypto";

  function getBaseName(file, inputPath) {
    const parsed = path.parse(file);
    const safeStem = parsed.name
      .toLowerCase()
      .normalize("NFKD")
      .replace(/[\u0300-\u036f]/g, "")
      .replace(/\s+/g, "-")
      .replace(/[^a-z0-9-_]/g, "")
      .replace(/^-+|-+$/g, "");

    const hash = crypto
      .createHash("sha1")
      .update(fs.readFileSync(inputPath))
      .digest("hex")
      .slice(0, 10);

    return safeStem ? `${safeStem}-${hash}` : hash;
  }

- If content references optimized files by deriving names from upload names,
  update getImageSet() so it uses the same naming strategy. This is important:
  the optimizer and the page helper must agree exactly.

Alternative:
- Keep optimized filenames based on the original stem, but add a manifest:

  public/images/optimized/manifest.json

  {
    "/images/uploads/картонче.png": {
      "small": "/images/optimized/abc123-400.webp",
      "medium": "/images/optimized/abc123-800.webp",
      "large": "/images/optimized/abc123-1200.webp"
    }
  }

- Then getImageSet() can read or import the manifest instead of guessing names.

Regeneration:
- Do not blindly skip existing outputs.
- Either:
  - regenerate every optimized image on each build, or
  - compare source modified time to output modified time, or
  - use content hashes in output filenames so changed files naturally produce
    new optimized filenames.

Notes:
- The manifest approach is more robust long term, especially for CMS uploads.
- It also makes Cyrillic, spaces, duplicate filenames, and replaced files much
  safer.
